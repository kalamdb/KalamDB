# KalamDB 0.7 Program

**Status:** Active  
**Target version:** 0.7  
**Date:** 2026-09-01

0.7 is not three independent projects. It is one release whose product bar is: typed nested data that persists and executes correctly, equality lookups that stay prefix scans as tables grow, and SQL-defined server procedures that use those same types.

Implement these three plans together:

| Track | Plan | 0.7 product outcome |
| --- | --- | --- |
| **Serialization** | [2026-02-14-flatbuffers-flexbuffers-vortex-migration-plan.md](2026-02-14-flatbuffers-flexbuffers-vortex-migration-plan.md) | One `kalamdb-serialization` crate. Nested `STRUCT` / `CREATE TYPE` / `List` persist through that crate only. |
| **Scalar secondary indexes** | [2026-08-30-scalar-secondary-indexes.md](2026-08-30-scalar-secondary-indexes.md) | USER/SHARED scalar `CREATE INDEX`, hot prefix seek, cold bloom/min-max prune, CLI schema-diff, RLS membership bind. |
| **Functions V1** | [functions-v1-implementation.md](functions-v1-implementation.md) ([design](functions.md)) | SQL procedures, generated SDKs, nested typed `CALL`, transactional topics, durable triggers. |

Do not ship 0.7 with only one of these. Nested procedure types without a central codec fork persistence. Indexes that keep JSON PK lists fight the serialization migration. Functions that scan `WHERE conversation_id = ?` stay too slow for the chat/RLS workloads 0.7 is supposed to carry.

Detailed tasks stay in the three source plans. This document is the combined sequence, shared ownership, and release gate.

---

## Why these three together

```text
SQL contract (tables, CREATE TYPE, CREATE INDEX, CREATE PROCEDURE)
        │
        ▼
ContractSnapshot / TableDefinition / TypeId
        │
        ├─► kalamdb-serialization     persist STRUCT/List/rows/catalog/index values
        ├─► indexing core             prefix seek + flush prune for equality
        └─► kalamdb-functions         CALL / nested ctx.functions / triggers
                │
                └── uses the same types, same row codec, same indexes
```

- Functions V1 requires recursive `STRUCT`/`List` in storage, catalog, Parquet, and the V8 ABI. That codec belongs in `kalamdb-serialization`, not a functions-only serializer and not a second copy in `kalamdb-commons`.
- Secondary indexes must not invent another persistence format. Index catalog rows go through the same object protocol; non-unique index values must leave JSON as part of the serialization track.
- Chat history, reconnect snapshots, and RLS membership bind are `WHERE col = ?` scans today. Procedures and live SQL on those tables need the indexes in the same release or 0.7 still full-scans as rooms grow.

Not in 0.7 (stay on the source plans' non-goals): Vortex-as-Parquet, schedules/`CREATE EVENT`, extra function runtimes, unique-by-default scalar indexes, ANN answering scalar equality.

## Shared rules

1. **One persistence codec.** Callers never choose FlatBuffers/FlexBuffers/JSON for RocksDB objects. Functions, indexes, topics, Raft durable payloads, and system catalog use `kalamdb-serialization`.
2. **One type system.** `CREATE TYPE`, table row types, and procedure signatures are SQL contracts. Arrow/DataFusion is the in-memory model. SDKs project; they do not define a parallel schema.
3. **One indexing core.** Scalar USER/SHARED indexes extend `IndexDefinition` / `IndexedEntityStore`. Vector hot PK uses that core. Do not add a functions- or RLS-specific index runtime.
4. **One CLI schema surface.** `kalam-schema-diff` must emit `CREATE TYPE`, `CREATE INDEX`, and `CREATE PROCEDURE` from local SQL. Generation and deploy compile local files; they do not require a live server to know the contract.
5. **Do not duplicate work.** Functions Task 3 nested serde **is** serialization Phase 2 (row `STRUCT`/`List`). Index JSON replacement **is** serialization Phase 4. Do not implement either twice.

## Combined sequence

Work the three tracks in parallel, but honor these hard edges.

### Wave 1 — Foundations (parallel)

| Track | Do now | Do not start yet |
| --- | --- | --- |
| Serialization | Phase 0 inventory/baseline. Phase 1 crate + envelope + CI report-only guard. Phase 2 row codec move, ordinal fields, recursive `STRUCT`/`List`. | Raft/stream cleanup (Phases 5–6). |
| Indexes | Task 1 DataFusion inventory (written decision only). | Hot seek that assumes a new catalog shape before Task 2. |
| Functions | Task 1 dialect/contract models and ADR for `kalamdb-functions`. Task 2 compiler/Arrow resolver (in-memory types only). | Catalog persist of nested values, V8 ABI, or a private codec. |

**Wave 1 gate:** Nested `STRUCT`/`List` round-trip through `kalamdb-serialization` with no string fallback. Dialect accepts `CREATE TYPE`, optional `ROW TYPE`/`FROM TABLE`, and reserved `UNION`/`INTERFACE` errors. Index plan has a written DF seek-vs-planner decision.

### Wave 2 — Catalog and hot path (parallel after Wave 1 gate)

| Track | Do now | Coupling |
| --- | --- | --- |
| Serialization | Phase 3 `EntityStore` / `IndexedEntityStore` call the central API. Models lose persistence `encode`/`decode`. | Index `TableDefinition` serde and function catalog rows use this boundary. |
| Indexes | Tasks 2–5: catalog on `TableDefinition`/`system.schemas`, extract one prefix adapter, open stores with catalog indexes, hot `scan` seek. | Do not persist index catalog or index values as ad-hoc JSON. Use the object protocol (or raw PK key bytes where the serialization plan allows). |
| Functions | Task 3 catalog providers. Consume the Wave 1 nested codec; do not extend `kalamdb-commons` codecs. Task 4 local generate. | `system.types` / `system.routines` persist like other catalog objects. |

**Wave 2 gate:** `SELECT … WHERE conversation_id = ?` seeks the scalar index on hot data. Function catalog rows and nested table columns persist through `kalamdb-serialization`. Local generate produces typed clients from SQL without a running server.

This is Functions Checkpoint A plus indexes hot-path proof, with the codec crate in place.

### Wave 3 — User-facing SQL and execution

| Track | Do now | Coupling |
| --- | --- | --- |
| Serialization | Phase 4 system/topic/vector cleanup, including secondary-index JSON → object encoding. | Coordinate with index CF value format so backfill and prefix scan stay compatible. |
| Indexes | Tasks 6–9: scalar `CREATE INDEX`/`DROP INDEX` DDL, CLI schema-diff, flush blooms/min-max, RLS membership prefix bind. | Same `CREATE INDEX` grammar in dialect, schema-diff, and example `schema.sql`. |
| Functions | Tasks 5–9: V8 spike, artifact activation, typed `CALL`, nested txs/context, transactional typed topic publish. | Procedure args/results and topic payloads use the shared value codec. Nested in-process calls still pass Arrow values without bytes. |

**Wave 3 gate:** Functions Checkpoint C (generated client → `CALL` → nested DB/topic → typed result). Indexed equality works after flush (cold prune). CLI diff emits index DDL. Index values are not JSON.

### Wave 4 — Durability, cleanup, 0.7 gate

| Track | Do now |
| --- | --- |
| Serialization | Phases 5–8: Raft, stream logs, delete old commons codecs, blocking CI guard, benchmarks. |
| Indexes | Task 10: chat realtime bench with `CREATE INDEX` on messages/members; docs/skills. |
| Functions | Tasks 10–12: durable triggers, `kalam deploy`/`kalam dev`, security/observability/docs. |

Stop at each functions checkpoint and at each wave gate. Do not start schedules or extra runtimes as part of 0.7.

## Crate ownership for 0.7

| Crate | Owns | Must not own |
| --- | --- | --- |
| `kalamdb-serialization` | Persisted-object protocol, row/object codecs, versioning, nested `STRUCT`/`List` storage tags | SQL parsing, index key layout, V8, HTTP/PGWire |
| `kalamdb-commons` | Domain IDs, `KalamDataType`, `TableDefinition`, contract value models | FlatBuffers/FlexBuffers, `encode`/`decode` on models |
| `kalamdb-store` / optional `kalamdb-index` | Prefix keys, CFs, `IndexDefinition`, atomic index writes | A private JSON/binary value codec |
| `kalamdb-dialect` | `CREATE TYPE`, `CREATE INDEX`, `CREATE PROCEDURE`, contract compiler | Storage bytes |
| `kalamdb-functions` | Runtime ABI, V8 adapter, revision cache | Persistence codec, scalar index implementation |
| `kalam-schema-diff` / CLI | Local compile, diff, generate, deploy | Live-server-only contract discovery for these objects |

## 0.7 release gate

Ship 0.7 only when all of the following are true.

**Serialization**

- `kalamdb-serialization` is the only internal persisted-object codec crate.
- Nested `STRUCT` / named `CREATE TYPE` / `List` round-trip without JSON intermediates or `ScalarTag::Fallback`.
- Direct FlatBuffers/FlexBuffers usage outside that crate is CI-blocked (after the report-only period).
- Definition of done in the serialization plan holds, including index values no longer stored as JSON.

**Scalar secondary indexes**

- USER/SHARED tables honor catalog scalar indexes on hot seek and on flush/compaction prune.
- `CREATE INDEX` / `DROP INDEX` parse, persist on `system.schemas`, and round-trip through `kalam-schema-diff`.
- RLS membership bind prefix-scans an indexed principal column.
- Chat realtime bench no longer full-scans `messages` / `conversation_members` for the documented equality filters.

**Functions V1**

- Functions plan final release gate holds: local `ContractSnapshot`, typed `CALL`, nested calls/context, transactional topics, durable triggers, CLI deploy/dev.
- Procedure and topic payloads use the shared codec; there is no functions-only serializer.

**Together**

- A representative chat schema with `CREATE TYPE`, scalar indexes, and `CREATE PROCEDURE` compiles locally, deploys, serves indexed SQL, and executes typed `CALL` / nested procedures on those types.
- Backend/CLI smoke tests and the production-like server build pass.
- No track is deferred to “right after 0.7” while still claiming 0.7 complete.
