# Per-surface atomicity, isolation, and durability

This matrix is the advertised promise for the current epoch. It follows Owner Decision 3 in `specs/038-unified-sdk-contracts/spec.md`: multi-row and multi-statement atomicity applies inside an explicit transaction on one data group, and inside a transactional server routine, for `USER` and `SHARED` tables. `STREAM` and `SYSTEM` tables stay autocommit. A write that would span data groups is rejected before commit.

Raft replication of one data group is not a claim that every SQL statement, live event, topic delivery, file object, or backup is globally serializable.

| Surface | Atomicity | Isolation and freshness | Durability and failure | Retry |
| --- | --- | --- | --- | --- |
| `single_sql_statement` | Autocommit. One row and its indexes are stored in one batch. A multi-row statement is not an all-or-nothing transaction unless the caller opened one. | The statement reads the committed snapshot visible to its session, plus its own writes in that statement. | Acknowledged autocommit follows the group's commit. A later row error can leave earlier autocommit rows committed. | Safe to retry only when the statement is idempotent. |
| `http_sql_batch` | Statements outside `BEGIN`/`COMMIT` are autocommit, one statement at a time. An explicit transaction in the batch uses the explicit-transaction row. A batch that ends with an open transaction is rolled back. | Same session snapshot as a single statement. Staged transaction writes are visible to later statements in that transaction. | Commit acknowledgement is the group commit. A failed statement rolls back only the open explicit transaction, not earlier autocommit statements. | Do not retry a batch that already committed an autocommit prefix unless each statement is idempotent. |
| `explicit_transaction` | Commit and rollback cover every staged `USER` and `SHARED` mutation in one data group. Cross-group writes are rejected before commit. `STREAM` and `SYSTEM` are rejected. | Read-your-writes for staged mutations. Concurrent transactions follow the coordinator's snapshot for that group. This is not a cross-group serializable order. | Success means the group accepted the commit. An unknown response after the commit request is committed or not committed; it is not a silent partial commit. | Retry only with a new transaction. Do not assume the first attempt aborted. |
| `native_function_call` | A root routine that owns a request transaction rolls that transaction back on failure. Nested calls share the root transaction, security context, and deadline. The atomic set is the same `USER`/`SHARED` single-group set. | Nested SQL sees the root transaction's staged writes. Invoker and definer rights stay those of the routine definition. | The database outcome commits with the root transaction. External HTTP and webhook work is post-commit and at-least-once. A lost response after commit is an uncertain outcome, not a rollback. | Retry a volatile routine only with an idempotency key. Do not resend a call that may already have committed. |
| `pgwire` | Uses the same coordinator as HTTP SQL. Explicit transactions are one data group. Autocommit statements follow the single-statement row. | One connection has one session snapshot and one open transaction block. | Commit acknowledgement matches the explicit-transaction row. Disconnect rolls back an open transaction. | The client must check the transaction outcome before retrying. |
| `live_subscription` | Not a transaction and not a commit boundary. Events describe commits that already happened. | Delivery is a consistent change stream for the subscription scope after the snapshot frontier. It does not freeze a multi-group global order. | A subscriber can observe duplicates, reconnects, and gaps that require a new snapshot. Acknowledgement of a live frame is not durability of the underlying write. | Resume from the advertised cursor. A gap replaces the stream with a new snapshot; it does not invent missing events. |
| `topic_consumer` | Outbox intent for the same data group commits with the table write. Consumer delivery is not part of that database transaction. | The consumer reads committed outbox records. It does not see uncommitted transaction state. | Delivery is at-least-once after commit. External side effects can be duplicated. | Handlers must be idempotent on the outbox identity. |
| `file_attachment` | File bytes and the referencing row are not one atomic commit. A failed upload does not become a committed row reference, and a rolled-back row does not prove the object was never stored. | Authorization checks the row and the file reference on later reads. | Orphan cleanup is a separate idempotent pass. A crash can leave an unreferenced object until cleanup. | Retry the upload and the row write with the same file identity. Do not treat object storage as transaction rollback. |
| `backup_restore` | A backup has one documented frontier for the catalogs and data groups it captured. It is not a cross-group point-in-time snapshot and not PITR. | Restore reads the captured frontier in an empty environment. It does not claim linearizability with writes that happened during the backup. | A completed restore can serve the captured committed prefix. A corrupt or partial backup fails instead of opening as an authoritative database. | Restore again into an empty environment. Do not retry by overwriting a live database. |
