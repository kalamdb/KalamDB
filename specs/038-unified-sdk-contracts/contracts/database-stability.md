# Database stability and application correctness contract

**Revision:** 2026-10-22. **Status:** required future evidence, not executed tests or a certification. Applies to the new format/API cohort only. Linked from [application contract](application-development.md), [readiness matrix](../app-readiness.md), [performance contract](serialization-performance.md), [spec](../spec.md) and [task extension](../tasks-app-stability.md).

## 1. Define the promise before testing it

Publish a machine-readable and human-readable guarantee matrix for each surface: single SQL statement, HTTP SQL batch, explicit transaction, native function root/nested call, PGWire/FDW, live subscription, topic consumer, durable action, file attachment and backup/restore. Each row states atomicity scope, isolation/read freshness, commit acknowledgement/durability mode, retry rules, failure/uncertain outcomes, table kinds and supported data-group boundaries.

Do not label the database globally serializable or linearizable merely because it uses Raft. SQL snapshot isolation, single-key linearizability, serializable transactions, global cross-group ordering and live delivery are different promises. The test oracle must match the documented promise. Unsupported isolation syntax fails explicitly rather than being accepted and ignored.

Current source evidence requires particular attention: docs/architecture/transactions.md says direct provider DML callbacks do not add statement-wide atomicity, while explicit transactions are constrained to one data Raft group and reject System/Stream table classes. Reverify current code, then close this gap or reject/reroute affected public operations before advertising atomic SQL statements. Generated RPC and a transaction wrapper alone do not establish serializability, constraint correctness or exactly-once external effects.

For supported USER/SHARED SQL statements advertised as PostgreSQL-compatible, a failure on a later row must not leave earlier rows partially committed. Required business commands must be atomic within the supported domain. If implementation cannot enforce the contract, the capability and example are blocked; weaker behavior is not silently hidden behind the SDK. Same-epoch schema evolution remains supported even though pre-release historical data import is not required.

## 2. Test harness architecture

Reuse existing Rust unit/nextest, CLI e2e, PGWire tests, SDK real-server tests and serialization fuzz harnesses. Add small deterministic fault hooks at the existing transaction/applier/store/flush/raft/publication boundaries rather than a second database execution engine. Hooks are test-only, unavailable in production builds and cannot be activated by public request metadata.

A seeded clock/network/storage scheduler makes ordering faults repeatable where feasible. Full FoundationDB-style simulation is not claimed or required as an immediate rewrite: start with deterministic component histories and actual-process fault injection. Keep separate tests on real RocksDB/filesystem/processes because mocks cannot prove persistence behavior. Testkits for application authors use isolated real backends and typed identity fixtures; UI/model mocks are labeled and never substitute for durability/RLS checks.

Every failure artifact contains seed, commit, toolchain/lockfile, schema, generated SDK versions, principals (without secrets), history, injected fault point, durability config and a minimized replay command. A discovered bug becomes a retained regression. Retry-to-green is not a passing assertion. Negative tests first prove that a legitimate positive control works, so a broken environment cannot make every denial test pass.

## 4. History and fault models

Capture invocation/completion, return values, known commit IDs/receipt keys and topology. Use linearizability checkers for operations whose contract is linearizable, and transactional anomaly/history checks for the declared isolation. Do not pass a weak register checker and claim serializable multi-table transactions. Include a negative-control implementation or seeded anomaly to prove checkers fail when the property is violated.

In an acknowledged durable mode, client-observed success must survive the supported quorum/process/storage failure envelope. Unknown completion is neither automatic failure nor automatic success; the history model permits either consistent outcome. Test membership changes and shard placement with supported scope, not invented global order. Peer authentication and role checks apply independently from correct Raft behavior.

Pair deterministic simulated delays with real node partitions and process restarts. Vary disk/network slowdown, timeout order, lease expiry, wall-clock adjustments and monotonic-clock scheduling. Fault hooks must not change the durable algorithm into a special test-only implementation.

## 5. New-data backup and schema changes are not old-version compatibility

The owner removed old release data/API preservation requirements. Do not reintroduce old readers or migration adapters. Nevertheless current-epoch data, backups, receipts and live history must remain correct across ordinary restart, restore and supported DDL. Backups include metadata plus data references and required runtime artifacts; secrets are handled by an explicit external configuration/restore procedure, not dumped into public manifests.

If a multi-group consistent checkpoint cannot be created, document the supported backup consistency boundary and block stronger claims. Snapshot consistency, retention and active readers must coordinate. Restore drills never overwrite production and verify the restored environment cannot deliver jobs/webhooks to production providers by default. PITR/branching/rolling mixed-release support is not implied by a basic same-format restore.

## 6. Execution cadence and evidence

**Per change:** compile/codegen/type-negative checks, codec and policy fixtures, focused DB invariants, previous bug seeds and a real single-node app smoke. Auth/transaction/storage changes must trigger the corresponding DB suites, not only SDK tests.

**Nightly:** randomized schema/query histories, bounded fuzz campaigns, real three-node failover/partitions where clustering is advertised, mixed hot/cold flush tests, varied fault seeds, resource pressure, cross-runtime and current-format crash/restart scenarios. Publish seed count, operations, runtime and uncovered combinations; test count alone is not coverage.

**Release:** all mandatory DB cases on the supported platform/durability matrix, multi-node evidence for advertised clustering, restore from independently stored backup, application fixtures, sustained mixed workload with fault/pressure phases and the existing CPU/memory/p99 gates. A proposed minimum is 24 hours of automated sustained mixed workload with bounded resources; this is a coverage floor, not a reliability theorem. If capacity is unavailable, record the missing test and do not claim its guarantee passed.

Use repository nextest/dev-build conventions for routine tests; explicit benchmark/optimized arithmetic profiles must be documented and identical across comparisons. Timeouts follow measured healthy execution with headroom, not arbitrary sleeps. Run fuzz/sanitizers/Miri/model checks where supported, recording scope and duration. Failures retain artifacts and cannot be quarantined silently to obtain a green release.

## 7. Gate STABLE

For every advertised capability, record test IDs, exact commit/lockfile/config, actual commands, pass/fail/artifact links and known limitations. No unresolved data-loss, security-isolation, false-atomicity, wrong-result or corruption defect may be waived by a performance result. Fix a defect or remove the affected capability from the advertised release with explicit approval; do not quietly weaken the test oracle.

Gate STABLE and Gate APP extend the current Gate R; they do not replace the codec security/performance gates or resurrect backward compatibility. Source review, a mock test, documentation completeness, finite fuzzing and code coverage alone do not certify a stable database. The output is reproducible evidence for a precisely stated failure model.

## Sources and adaptation

[SQLite testing](https://www.sqlite.org/testing.html) motivates allocation/I/O/crash/malformed-file and invariant coverage. [FoundationDB simulation](https://apple.github.io/foundationdb/testing.html) motivates deterministic failure seeds plus real systems testing, not a claim that KalamDB already has Flow simulation. [Jepsen consistency models](https://jepsen.io/consistency) supplies precise history properties. [PostgreSQL 18 isolation](https://www.postgresql.org/docs/18/transaction-iso.html) is the oracle for the explicitly compatible subset, not a blanket statement of KalamDB parity. [SQLancer](https://github.com/sqlancer/sqlancer) supplies metamorphic/oracle patterns; adapt a supported dialect/provider rather than claiming arbitrary generated SQL is valid for KalamDB. All research was reviewed on 2026-10-22; runtime evidence is still pending.
