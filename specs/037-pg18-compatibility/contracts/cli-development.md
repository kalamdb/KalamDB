## One project snapshot and one diff plan

Load the configured SQL file or directory into one immutable project revision: source paths/content hashes/spans, identity manifest, resolved target and schema/search_path, relevant configuration and toolchain/capability versions. Missing/unreadable source is an error; it is not an empty desired schema. A transient truncated file must not authorize mass deletion. File and directory sources must work consistently through generation, diff, watch, baseline and apply.

Parse each unchanged source once per cached revision with the shared dialect AST. Derive structural tables and contract types/routines from that representation. Reuse it for diff, generated bindings, function artifacts, manifest and diagnostics instead of reading/reparsing schema.sql independently at each stage. A standalone command may construct a fresh snapshot; a file edit creates a new revision. No user-SQL text rewrites to erase table/type clauses. Runtime and CLI share semantic models and resolver rules; the CLI snapshot is a derived project model, not another live type registry.

Use the actually resolved target, not a hardcoded `public` or only `project.default_env`, for unqualified declarations. Preserve quoted identifiers and component boundaries everywhere. Define deterministic multi-file search-path scope and reject ambiguous declarations; filesystem sort order must not become a substitute for dependency analysis. Supported declarative statements must change the model; unsupported valid SQL must produce a located actionable diagnostic, never silently disappear or yield “no changes”. Arbitrary data updates stay in explicit migrations/seed files.

## Diff coverage and migration intent

| Object family | Required declarative changes and boundary |
| --- | --- |
| Schemas | Create, explicitly identified rename/move, ownership/privileges and reviewed deletion of managed objects; default/public and quoted names follow G2. |
| Tables/columns | Add/remove/rename; defaults, nullability, canonical types/modifiers/collations, identity/generated columns, constraints/FKs/indexes and supported table properties. Preserve data through legal ALTER; explicit USING/backfill where needed. |
| Types | Enum/composite/domain create and legal alterations, comments, dependent arrays/table row types; stable member/field/type identities. Range/base/shell forms follow T124's explicit supported/gap inventory. |
| Functions/procedures | Signature-aware add/remove/replace, modes/defaults/results, language/body/security/settings, grants/comments and declared dependencies. Use FUNCTION/SELECT versus PROCEDURE/CALL correctly; new overload versus replacement must be visible in the plan. |
| Related objects | Views, sequences and their ownership/state, supported triggers, policies/RLS, topics/sources and schedules must have inventoried diff coverage or a blocking manual-migration diagnostic. Existing Kalam-specific objects remain covered. |

Emit PostgreSQL `ALTER COLUMN ... TYPE`, `SET/DROP DEFAULT`, `SET/DROP NOT NULL` and other appropriate clauses; stop emitting `MODIFY COLUMN` on the canonical surface. A comment saying “manual review required” is a blocked operation, not a successful no-op. The baseline cannot advance past a requested change that was only emitted as a comment. A required backend operation that is not implemented remains a capability gap.

Renames and schema moves require unambiguous identity continuity from the existing identity manifest or an explicit reviewed migration. Never guess a rename from similar names/fields and never silently drop/recreate as a substitute. Extend the existing identity mechanism to affected managed objects rather than inventing incompatible IDs in each generator. Enum label removal/reorder and incompatible routine results require explicit dependency/data migration; type recreation is not automatically safe. Semantically unchanged SQL yields no executable migration or function activation; preserve body text/literal meaning while normalizing only valid SQL equivalences.

Use a typed operation plan with identity, before/after descriptors, dependencies, prerequisites, risk, transaction grouping, reversibility and source location. SQL and human/agent summaries derive from it. Explicit SQL migrations use the same parser/risk analysis but preserve user-declared ordering and transaction boundaries. Do not mix partial desired-state reconstruction with arbitrary imperative SQL replay.

## Dependency ordering and destructive changes

Create dependency order from the object graph, and drop in reverse dependency order. A fixed “tables, then types, then routines” concatenation is invalid. Cover named type → column → row type → routine → trigger, routine-backed defaults, views, domain/check functions, foreign keys, grants and cross-file references. An implicit table row type is owned by its table, not emitted independently. Use legal deferred constraint/body-binding phases where available; otherwise report a dependency cycle with locations and a required manual migration. String-language bodies may have dependencies PostgreSQL itself cannot infer; record that limit and fail on known dangling dependencies rather than claim complete static discovery. [PostgreSQL dependency tracking](https://www.postgresql.org/docs/18/ddl-depend.html).

Group operations by actual transaction capability. For an existing enum, adding a value and immediately using it may require a commit boundary; PostgreSQL does not allow using a value added in a transaction before that transaction commits. A supported `CREATE INDEX CONCURRENTLY` cannot be forced into a transaction block. Unsupported variants fail before effects. Such phases require durable progress and explicit partial-completion recovery, not a blanket “all migrations are atomic” promise. [ALTER TYPE](https://www.postgresql.org/docs/18/sql-altertype.html), [CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html).

Classify data loss, rebuilds, narrowing casts, constraint changes, schema/type/routine removal, privilege broadening and CASCADE impact from typed operations/AST. Do not search raw lines for `DROP`: routine bodies, comments and quoted names are not DDL operations. Apply the same classification to generated and manual migrations. `--force` authorizes the existing development policy for the displayed target/plan, not bypassing stale-plan checks, permissions, unsupported operations or target ownership. Agent mode remains noninteractive and refuses destructive work without the required explicit option. Preserve the existing interactive draft review flow; never silently reset a schema to recover from an error.

## Baselines, drift and multiple environments

Separate desired source revision, committed database revision, generated artifact revision and active function revision. A baseline is evidence of committed managed state, not simply a copy of today's source file.

Bind baseline metadata to project/managed scope, stable server/database identity, target schema identities, migration checksums/head, relevant catalog revision and the exact applied source hash. URL alone is insufficient after reset/recreation. Stage atomic local baseline writes from the captured source revision only after the corresponding database receipt is known. Generation-only, skipped, pending-review, unsupported or failed work cannot advance an applied baseline. A source edit during apply remains a later unapplied revision.

When the local cache is absent or belongs to a different target, reconstruct expected managed state from verified applied migrations/snapshots and reconcile authoritative catalog evidence. Do not seed from current desired schema merely because numbered filenames appear applied: the desired file may already contain unapplied edits. Validate applied checksums, missing history files, branch switches, restore/reset and out-of-band DDL. Keep remote pull out of scope; read-only drift detection does not replace the local source of truth. Never delete unmanaged remote/shared objects because they are absent from a project's source.

## Apply, publication and recovery

Each cycle freezes its inputs and follows this state machine through existing workflow owners:

1. **Prepare**: load/resolve/validate the desired snapshot; compute typed operations, target prerequisites and risk. Stage generated contracts and compile/typecheck the function artifact against that exact snapshot before any schema effect. A required compiler that is absent is a build failure, not a verified build.
2. **Review/admit**: apply current interactive/agent policy; acquire target-scoped migration coordination and validate the expected migration/catalog heads. A stale plan replans before effects; concurrent dev/migrate/deploy clients must not both apply it.
3. **Apply**: execute supported transactional groups on one actual transaction/session. The migration receipt and transactional DDL commit together. For nontransactional phases, persist fenced progress and outcome evidence; do not replay completed destructive work after a timeout.
4. **Publish server state**: activate the staged executable against the committed signature/type/ABI revision with compare-and-swap. For incompatible routine changes, require an atomic server catalog/artifact binding handoff or block the change until that capability exists. Never expose a new signature with a mismatched old artifact. Concurrent publication and rollback verify expected active revision.
5. **Publish local state**: record the exact committed baseline; publish generated output/artifact manifests from staged files, with completion markers or directory swaps so readers never see mixed revisions. Keep user-written handlers untouched. Restart/reload configured app processes only after their required generation/activation stages succeed.
6. **Report**: expose per-stage states and pending work; a later source revision schedules another cycle. “Ready” must identify what actually succeeded.

Filesystem writes, database commits and module activation are not a single distributed transaction. If the database committed but activation/codegen failed, record `database committed; activation/generation pending`, keep only compatible previous artifacts callable, and retry the failed stage from its recorded revision. Do not rerun DDL, claim the old schema is still active or manufacture a rollback. A backend unable to provide the required safe handoff is a blocking capability gap.

Use one client/server migration authority and coordination boundary shared by `dev`, migration apply and deploy. Cross-process locks/leases require owner identity and fencing; a killed client cannot retain indefinite ownership or later publish a stale revision. Explicitly handle failure before DDL, after DDL but before response, after commit, after baseline write, and during activation/file publication. After an unknown commit outcome, reconcile the server receipt before retry. Missing local migration files do not turn failed/partial history into success. Keep checksums, repair actions and non-reversible DOWN notes truthful; function rollback does not roll back tables or data.

Migration `-- UP` / `-- DOWN` markers count only as top-level marker comments outside SQL strings, dollar bodies and nested block comments. Use the shared lexer/source boundaries for batching; preserve routine semicolons, tags and explicit transactions. A marker-like line inside JS/SQL/PLpgSQL is body data, not a file section. A hand-written migration is never silently truncated at it.

## Watch loop, memory and feedback

Watch schema files/directories, identity manifests, relevant configuration, function inputs and dependency lockfiles. Detect create/delete/rename/atomic-save and same-mtime changes. Exclude generated/build outputs, dependencies and runtime/log directories; generated JS must not trigger its own rebuild indefinitely. Define symlink traversal/cycle and source-count/size limits. A bounded event set with debounce/coalescing is preferred; overflow triggers bounded rescan, not lost changes. The same correctness rules apply to a polling fallback.

Maintain separate observed, in-flight, successful and retry-needed revisions. A save during compile/apply cannot be acknowledged by sampling the latest mtime afterward. Before effects, superseded work can be cancelled and replaced; after effects start, reconcile that revision's outcome and queue the latest pending revision. Transient network/activation failure retries with bounded backoff without needing another edit. Invalid source waits for a correction without retry storms. Schema/function generation failure must not activate a module built against an unapplied revision.

Reuse the parsed snapshot and cached generated layouts across one cycle; hash all actual build inputs, toolchain/ABI and dependency versions, not just contract text. Do not cache credentials or security decisions in shareable generated artifacts. Skip unchanged writes, uploads and builds. Bound source/AST/artifact caches, queued work, logs, retries and child processes; terminate compiler/process trees on cancellation and keep the existing managed database ownership rules. Measure idle CPU and edit-to-ready time independently from database query runtime.

## Command lifecycle parity

| Journey | Required behavior |
| --- | --- |
| `init` → `dev` | Fresh project produces valid PostgreSQL-shaped schema/type/routine definitions, installed required build tools, generated clients and callable JS routines before reporting the relevant stage healthy. |
| `up` → `dev` → exit | Reuse only the registered project/global instance; leave a database started by up running. Dev-owned instances stop according to 035. |
| `status`, `logs`, SQL, `functions status/revisions/runtime/logs` | Resolve the same target and report schema, generation, activation and app state independently; logs/events include revision correlation and actionable errors without credentials. |
| `schema gen`, `functions build`, migration create/apply/status/repair | Consume the same resolved snapshot/plan/receipt contracts. Offline generation is identified as desired-state output, not proof of a database migration. |
| Function body-only edit / rollback | An external handler-only edit rebuilds/activates the artifact without a schema migration when its database contract is unchanged. An inline SQL-declared body change updates the catalog through legal routine replacement as well as its executable. Rollback refuses an incompatible historical artifact. |
| `dev --exec` | Create an isolated local target even with inherited remote/global selectors; apply the frozen intended schema/migrations, generate/build/activate required routines, seed, run the command, clean up owned resources and propagate exit/signal status. Pending drafts must be included under an explicit isolated-test policy or cause a clear error, not be silently omitted. |
| Seed/reset/down/restart | Seed after required dependencies/activation; respect once-per-database versus explicit rerun and no production auto-seed. Reset only the resolved owned local target; invalidate its baseline/history identity. Down stops the registered session/process tree while preserving data. |
| Named environment/global target/second checkout | Enforce managed scope, target-specific baselines/credentials and migration coordination; no project may infer ownership from an open port. Changing target cannot reuse another target's “synced” state. |
| Reviewed migration/deploy/fresh clone | Same plan and immutable checksums; dry-run reports blocking gaps and effects without writes. A clone rebuilds from recorded migration and artifact inputs. Capability/version negotiation rejects unsupported PG/ABI operations before DDL; deployment is not a watcher or an implicit reset. |

App health is a separate observation from database/schema readiness. Preserve existing `KALAM_READY` compatibility while adding explicit generation/function/app stage states and revision fields; do not redefine an old marker silently. A process that started and exited is failed, not healthy. If an app has no readiness probe, report `running`/`unknown health` rather than inventing one. Background dev start/status and agent automation must inspect the required stage states. Schema watch errors keep the existing processes running per 035, but report stale/degraded state instead of claiming the desired revision is active. Preserve the T123 rule: schema/type changes require subscription reconnect, not transparent live-subscription migration.

`up` remains a database-only lifecycle command. If a configured seed depends on unavailable migrated objects or JS routines, report seed prerequisites as pending/failed and direct the user to the relevant preparation command; do not silently mark the seed complete or start an application/build pipeline inside up. A successful seed receipt is recorded only after completion. Reset/dev/exec use the shared preparation stages when those dependencies are required.

CLI-to-server SQL/artifact uploads still use network encodings. The zero-intermediate-serialization requirement applies to in-process query/function/V8 values; it does not forbid legitimate deployment or wire codecs. Build once per changed artifact and avoid repeat uploads of the same verified revision.

## Acceptance and performance gates

T151 must run an isolated disposable project against a real server: init → up/dev → create enum/composite/domain → dependent table → overloaded function/procedure → generate/build/activate → typed SQL and SDK calls → safe alterations/explicit renames → body-only edit → invalid edit/fix → reviewed destructive change → restart → fresh clone replay → function rollback compatibility → seed/reset/exec/down. Include quoted/dotted/Unicode names, arrays, defaults, tagged bodies and cross-file dependencies. Validate actual catalog/data contents and V8 ABI outputs, not only generated text or fake-server requests.

T152 injects save-during-build/apply, watcher overflow, deleted files, missing tools, typecheck/activation/app failure, permission failure, target switch, out-of-band drift, same-target concurrent clients, schema commit with a lost response, interrupted multi-phase migrations and stale rollback. Test no duplicate destructive effect, no wrong-target writes, no erased user handlers, no false readiness and bounded recovery. Existing fake-server tests remain useful for orchestration but cannot close SQL/runtime acceptance.

T153 preregisters small/large/multi-file project workloads and reports cold/warm/startup/edit-to-ready seconds, CPU, allocation, retained memory, parse counts, generated writes, uploads and process counts. An idle settled project does no repeated parse/build/upload/write; no-op edits cause no migration or activation. A semantic edit reuses one frozen snapshot, with bounded cache retention across many revisions. Compare the previous design and apply the existing regression budgets; claim faster/lighter development only from measurements. These CLI metrics supplement, not replace, SQL and V8 performance gates.
