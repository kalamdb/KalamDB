# Comparison run — 2026-10-08

Machine: **Apple M5 Pro**, 15 cores, 24 GB RAM.

Protocol unchanged: 16 in-flight HTTP requests, 100k insert wall, 10k insert
latency, 1M point reads. Timed reads consume response bytes and check HTTP
status only.

KalamDB server: fresh `cargo build --release -p kalamdb-server` immediately
before the suite (`0eac50be` plus uncommitted working-tree changes). The
tracks used port **2920** so they did not touch the dev server already
listening on 2900.

## Versions

- KalamDB **v0.7.1** (`0eac50be`), local `target/release/kalamdb-server`
- TrailBase **v0.34.4** (was v0.33.14)
- PocketBase **v0.40.5** (was v0.40.3)
- SurrealDB **v3.3.0** (was v3.2.4; GitHub latest. v3.2.5 is a later 3.2 patch)

KalamDB has two tracks on the same hot-only server config:

- **SQL** — parameterized `POST /v1/api/sql`
- **functions** — schema-first inline JS, `POST /v1/functions/bench/{insert_message,get_message}`

## Results

| Metric | KalamDB SQL | KalamDB functions | TrailBase | PocketBase | SurrealDB |
|---|---:|---:|---:|---:|---:|
| 100k inserts (wall) | 3.16 s | 11.94 s | 4.92 s | 14.01 s | 2.59 s |
| Insert p50 / p95 | 357 µs / 534 µs | 1.70 ms / 2.53 ms | 808 µs / 1.24 ms | 1.65 ms / 4.55 ms | 367 µs / 496 µs |
| 1M point reads (wall) | 14.01 s | 80.61 s | 12.48 s | 19.22 s | 14.77 s |
| Read p50 / p95 | 200 µs / 280 µs | 1.21 ms / 1.84 ms | 171 µs / 244 µs | 247 µs / 504 µs | 200 µs / 293 µs |

Raw logs: `kalamdb-20261008-204216.txt`, `kalamdb-functions-20261008-204234.txt`,
`trailbase-20261008-204441.txt`, `pocketbase-20261008-204501.txt`,
`surrealdb-20261008-204537.txt`.

Do not collapse this into a single “X is faster” headline. Writes and reads
rank differently, and KalamDB functions still pay V8 + nested SQL on every call.

Versus the 2026-09-30 run on this machine, TrailBase v0.34.4 is the large
shift: 1M reads went from 51.72 s to 12.48 s, and 100k inserts from 6.83 s to
4.92 s. PocketBase and SurrealDB stayed close to the previous run. KalamDB SQL
reads were a bit faster (14.64 s → 14.01 s); functions were a bit slower.
